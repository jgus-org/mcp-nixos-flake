# Recipe provenance

The `mcp-nixos` build in `flake.nix` is adapted from the nixpkgs recipe, so the question "what did we change" stays answerable after the pin moves. The base is nixpkgs `3ec636362e1816bc2f0888fa0fa2c69f1bc9e504`, whose recipe builds 3.0.1:

```console
$ git show 3ec636362e1816bc2f0888fa0fa2c69f1bc9e504:pkgs/by-name/mc/mcp-nixos/package.nix
```

| What differs, and why it is safe                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `version`, `sourceRev`, and `sourceHash` appear nowhere in the recipe: the leaf owns the fetch and the pin, where the base writes them as literals.                                                                                                                                                                                                                                              |
| `meta.changelog` is derived from the pinned version where the base reads it from `src.tag`.                                                                                                                                                                                                                                                                                                      |
| `meta.description` names Home Manager and nix-darwin beside NixOS; the base names only NixOS.                                                                                                                                                                                                                                                                                                    |
| `meta.maintainers` is dropped — nixpkgs-internal metadata that means nothing outside nixpkgs.                                                                                                                                                                                                                                                                                                    |
| `dependencies` names `python.mcp` and `python.pydantic` where the base names the fastmcp distribution; see the patch below.                                                                                                                                                                                                                                                                      |
| `patches` carries a standing port to the official MCP Python SDK. `patchFlags` is ours: the patch hook runs `patch ${patchFlags:--p1}`, so naming `--fuzz=0` replaces the hook's `-p1` rather than adding to it — hence `-p1 --fuzz=0`. Without the fuzz allowance a hunk whose context has drifted fails the build instead of applying two lines off, with a warning this file would never see. |
| `pythonImportsCheck` names `mcp_nixos.server` beside the base's `mcp_nixos`: importing the package alone never imports the module this patch rewrites, so the base's check would pass a tree whose server module fails to import. Everything else — `nativeCheckInputs`, `disabledTestPaths` (`tests/test_integration.py`, needs network) — is the base's.                                       |

## Standing patch

`patches/port-to-official-mcp-sdk.patch` rewrites the pinned upstream source (revision `6a517811658c21f97bd7703b35546085117fc310`, version 3.1.0) from PrefectHQ `fastmcp` onto the official MCP Python SDK. It is applied by the derivation, after unpack and before the build, so it is part of what this flake publishes rather than something a consumer opts into.

The fleet carries it because no nixpkgs channel can serve what upstream requires: upstream's floor is `fastmcp>=4.0.0`, `nixpkgs-unstable` at this lock carries `fastmcp` 3.4.7 with `fastmcp-slim` 3.4.7 marked broken beside `mcp` 2.3.0, and `nixos-26.05` carries 3.2.3 with no `fastmcp-slim` at all. Satisfying that floor meant maintaining a second producer (`flakes/fastmcp`) and an overlay on every build of this one. The SDK needs no such machinery: `python.mcp` 2.3.0 is in the channel this flake already locks.

Upstream is not moving on its own. Upstream `main` still requires `fastmcp>=4.0.0` and still carries a mypy override for `fastmcp.*`; the open pull requests extend its fastmcp-4 Nix integration. The patch is a fork-in-place, and the retirement condition below is the only thing that removes it.

No test file is disabled and no whole file is patched away. `tests/test_integration.py` stays in `disabledTestPaths` because it reaches the network — the base recipe's decision, unchanged.

`ToolError` is deliberately not imported, and that is a measured decision rather than an assumption about the code. mcp 2.3.0 treats the two failure kinds differently at the tool boundary: a raised `ToolError` keeps its own text after the prefix (`mcp/server/mcpserver/tools/base.py:156`), while any other raised exception is replaced by `Error executing tool <name>` and the exception's own message stays on the server (`tools/base.py:211-213`). A tool here that let an exception escape would therefore lose its text — so which paths raise matters.

None of them reach the boundary. Both raise sites in this source are converted one layer below the tool: `sources/base.py:94` raises `APIError("API error: Connection timed out")` on `requests.Timeout` and `:96` on `HTTPError`, and `utils.py:188-189` raises `DocumentParseError` (defined at `utils.py:117`, re-raised from `caches.py:500`, caught by name in `sources/nixdev.py:88`, `noogle.py:140,245,293,355`, `nvf.py:139,197,224,275`, `nixvim.py:44,71,131,189`) — but `sources/nixos.py:297-298`, `:421-422`, `:452-453`, `sources/base.py:257-258` and `sources/nixhub.py:106,195,262,395` each end in `except Exception as e: return error(str(e))`, so the message arrives in band as an `Error (...)` result with `isError: false`, exactly as it did on fastmcp.

Both paths were driven on both servers with one MCP client (probe output `/nix/store/0ianz06slwx9b65w9hlk89jsj0k4bin5-mcp-probe`): a proxy that accepts the `CONNECT` and never answers produces `Error (ERROR): API error: Connection timed out` after 20.0 s, and a local TLS-terminating proxy answering 404 produces `Error (ERROR): API error: 404 Client Error: Not Found for url: https://search.nixos.org/backend/latest-50-nixos-26.05/_search`. On both servers the `content` text, the `structuredContent.result`, and `isError: false` are byte-identical, so neither case is a delta. `isError: false` on an API failure is upstream's choice on both frameworks, not something this patch introduced.

### HTTP `Host` validation, which this patch does not touch

The SDK builds `TransportSecuritySettings` only for a loopback bind. `mcp/server/lowlevel/server.py:753` — the app `run(transport="streamable-http")` reaches through `MCPServer.streamable_http_app` (`mcp/server/mcpserver/server.py:1303`) — reads `if transport_security is None and host in ("127.0.0.1", "localhost", "::1")`, and what it builds is `enable_dns_rebinding_protection=True` with `allowed_hosts=["127.0.0.1:*", "localhost:*", "[::1]:*"]`. Any other bind leaves `transport_security` `None`, which the middleware reads as protection off. The same guard is repeated for SSE at `mcp/server/mcpserver/server.py:1164`.

`main` defaults `MCP_NIXOS_HOST` to `127.0.0.1` (`mcp_nixos/server.py:624`), so `MCP_NIXOS_TRANSPORT=http` with no other configuration takes the protected branch: a request whose `Host` is outside that allowlist is answered **421 Misdirected Request** where fastmcp answered anything. MCP clients send `Host: 127.0.0.1:<port>` and see no change; a loopback listener behind a proxy that rewrites `Host` does. `MCP_NIXOS_HOST=0.0.0.0` validates nothing, exactly as fastmcp did. The only in-tree consumer is stdio (`modules/agents/repository-files.nix:10`) and no `.nix` file in this repo sets `MCP_NIXOS_TRANSPORT` or `MCP_NIXOS_HOST`. Widening the allowlist is a consumer-facing behavior change, so if a consumer ever needs it, it belongs behind a reusable option on this producer — flake-lib's `AGENTS.md` requires an option for a behavior change, not a value baked into a patch.

Both sides were run side by side over HTTP for that row, each started with `MCP_NIXOS_TRANSPORT=http MCP_NIXOS_PATH=/mcp MCP_NIXOS_STATELESS_HTTP=1` and driven with `curl -X POST` and an `initialize` body (`/nix/store/yxn09w2h6yhwk2qxx0yk4069q7vlk2p0-host-probe`). The pre-port server (`/nix/store/am0xjfq4n76aa6iyisxqhgd4240bbk6h-mcp-nixos-3.1.0`) answered 200 to both the correct `Host` and `Host: evil.example.invalid` on the `127.0.0.1` bind (port 8911) and on `0.0.0.0` (port 8912). The patched server (`/nix/store/lbffah9pxhpd9r0rqi3lg23qsqhj8dpg-mcp-nixos-3.1.0`) answered 200/421 on the `127.0.0.1` bind (port 8913, server log line `Invalid Host header: evil.example.invalid`) and 200/200 on `0.0.0.0` (port 8914). Each wait for the first answer was bounded at 60 tries of 0.5 s and completed in 2.0-2.5 s, so no row here is an unstarted server.

Two caveats belong to that pair. The auto-built settings allowlist `Host` only: `Origin` validation stays off on every bind, which is what a request from a browser-hosted MCP client would need. And on the first attempt both sides showed `000` — no connection — because the build sandbox exports `SSL_CERT_FILE=/no-cert-file.crt` and `NIX_SSL_CERT_FILE=/no-cert-file.crt` (`/nix/store/7zrx5pkhv140nfg2qjcrg6cw3b9ck59y-sandbox-env`). The pre-port server cannot survive it: fastmcp's `httpx2._config.create_ssl_context` reads `os.environ["SSL_CERT_FILE"]` while the server is being constructed, so it aborts before the listener opens — the same difference the `SSL_CERT_FILE` row records, measured with the sandbox value in place at `/nix/store/xvcw37jf8swzqpmd8k5c1k99328livy7-host-probe`, where the pre-port side never answered and the ported side reported the 200/421 and 200/200 pair. Only the pre-port startup failure was measured; whether the ported server would fail an outbound request under the same value was not, and no fleet config sets that variable. Clearing it on both sides produced the matrix above.

### Client-visible change

Measured over stdio with one MCP client (`mcp` 2.3.0's own `Client`) against two builds of the same pinned upstream revision. The "before" side is the unpatched source built with the `flakes/fastmcp` overlay this branch deletes, which is the fastmcp every consumer of `packages.mcp-nixos` actually had: `python3.14-fastmcp-slim-4.0.5`, the release `flakes/fastmcp/pin.nix` carried (`version = "4.0.5"`, `sourceRev = "004bf15a2ba99f077160993c00a404e1a9da83ea"`), read off the built wrapper at `/nix/store/h3ilzbz4wszm0cb487zjx08bgvjngxz6-closure`. Server binaries: pre-port `/nix/store/am0xjfq4n76aa6iyisxqhgd4240bbk6h-mcp-nixos-3.1.0`, patched `/nix/store/lbffah9pxhpd9r0rqi3lg23qsqhj8dpg-mcp-nixos-3.1.0`. Raw dumps: `/nix/store/0ianz06slwx9b65w9hlk89jsj0k4bin5-mcp-probe`. The two builds resolve different nixpkgs revisions (the pre-port recipe resolves `nixpkgs-unstable` `13e53762c5afaf384d4614e94527a9ccfafe41d0`, this flake's lock `e62746b0b472753ef019baceab6f1e2e52014980`), but every runtime piece they share is the same store path — `python3-3.14.8`, `uvicorn-0.51.0`, `httpx-0.28.1`, `httpx2-2.13.1` (`/nix/store/h3ilzbz4wszm0cb487zjx08bgvjngxz6-closure`) — and each side's own validation error cites `errors.pydantic.dev/2.13/`, so nothing below is an interpreter or pydantic artifact. An earlier draft of this section measured the "before" side against fastmcp 4.1.6 from a scratch venv; that release was never in this root, and two of its rows were wrong (marked **reversed** and **wrong** below).

Unchanged, byte for byte, from the same dump: `serverInfo` (`mcp-nixos`, 3.1.0), the negotiated `protocolVersion` (`2026-07-28`), the 1848-character `instructions`, the tool names, every parameter description (all eight on `nix`, all three on `nix_versions`, identical lengths and text), parameter types, defaults, enums and `required` (`["action"]`, `["package"]`), tool result text, `structuredContent`, `isError`, and `resultType`. The table below is the complete output of a recursive diff of the two `tools/list` payloads and of the five tool-call cases — a difference list, not a selection.

Two rows changed verdict when re-measured against the pinned 4.0.5, and are called out rather than edited quietly:

- **Capabilities — reversed.** Against 4.1.6 this row read as the port losing `logging` _and_ losing `listChanged`. Against 4.0.5 the port loses `logging` and the `io.modelcontextprotocol/ui` extension but **gains** `listChanged: true` on prompts, resources and tools, plus `resources.subscribe: true`. A client that branches on `listChanged` behaves differently after the port; nothing in-tree does.
- **`nix` description — wrong.** It was recorded as 2665 → 3679 on the theory that fastmcp truncated the docstring at the blank line before `Notes:`. fastmcp 4.0.5 published the same 3678 characters the SDK publishes; the only difference is one trailing newline. There is no prompt-size change and no paragraph that fastmcp hid. (The truncation is real, but it is 4.1.6 behavior — which is exactly why measuring it here mattered.)

The one loss of strictness is the unknown-argument case: an argument name that is not in the schema is now ignored rather than rejected, because the SDK's generated argument model leaves pydantic's `extra` at `ignore` while fastmcp's forbids it — the `additionalProperties: false` in the table above is that same setting showing up on the wire. A misspelled `query` becomes an empty query and an unhelpful answer instead of a corrective error. Tightening it would mean patching the SDK, which is out of scope for this producer.

### Advancing the pin

`update-version` bumps `pin.nix` only; it never touches the patch. When the new revision has changed a patched region, the build fails at `applying patch` and names the hunk. Resolve it by hand:

```console
$ git clone https://github.com/utensils/mcp-nixos /tmp/reapply && git -C /tmp/reapply checkout <new sourceRev>
$ cp flakes/mcp-nixos/patches/port-to-official-mcp-sdk.patch /tmp/reapply/
$ git -C /tmp/reapply apply --3way port-to-official-mcp-sdk.patch   # resolve the conflicts
$ git -C /tmp/reapply add -N -u && git -C /tmp/reapply diff > flakes/mcp-nixos/patches/port-to-official-mcp-sdk.patch
$ nix build ./flakes/mcp-nixos#mcp-nixos    # doCheck is the gate; run ruff format before committing
```

A conflict in the `Annotated[...]` hunks means upstream edited a description: carry the new text into the `Field(description=...)` form, keep to `line-length = 120` (upstream's ruff setting), and re-diff the published schema before calling it done — a description that stops being published is invisible to a build that still passes.

## Tests

The suite runs in `doCheck` here — 429 tests in about four seconds — because the dependency closure under this application is what the conversion moved. That is an exception to the fleet default of `doCheck = false` for packaged upstreams: the upstream ran its own suite, suites are not free, and a resource-hungry suite times out on a loaded builder and reports a build break that is not one.

Both counts below were read out of `doCheck` logs from rebuilds run after the last edit to this tree (`nix build --rebuild`, since a cached output would report nothing). The unpatched pinned source, built with the recipe at HEAD plus the `flakes/fastmcp` overlay and no `patches`, reports `collected 431 items` / `431 passed in 4.93s` at `/nix/store/am0xjfq4n76aa6iyisxqhgd4240bbk6h-mcp-nixos-3.1.0`. This producer reports `collected 429 items` / `429 passed in 3.89s` at `/nix/store/lbffah9pxhpd9r0rqi3lg23qsqhj8dpg-mcp-nixos-3.1.0`, with the patch applied to all six files and the import check running both `mcp_nixos` and `mcp_nixos.server`. Neither run skipped or deselected anything. The 2-test difference is exactly the two `FASTMCP_ENV_FILE` tests the patch deletes; the 431 figure is the unpatched build's own count, not a number copied from upstream's README, which records no test count.

## Retirement

Two separate conditions, in order of likelihood:

- **Drop the patch** when upstream merges a port to the official SDK (nothing like it is in flight upstream as of the 2026-11-05 check). Then this producer keeps its recipe and loses `patches` and the dependency swap; the schema deltas above become upstream's problem, not the fleet's.
- **Delete this producer** and publish `pkgs.mcp-nixos` from nixpkgs once nixpkgs' own recipe builds the application at the pinned revision. That requires either the SDK port in nixpkgs' own source or a channel carrying `fastmcp>=4.0.0` with a non-broken `fastmcp-slim`; no channel this fleet tracks meets either today.
